# MVP Limitations & Device-Test Checklist

Everything here is an honest ceiling of the current implementation, not a
product decision. PRD intent is preserved via documented fallbacks (AGENTS 34).

## Known limitations

| # | Limitation | Cause | Upgrade path |
|---|-----------|-------|--------------|
| 1 | YUV stills come from the ImageAnalysis stream and are far below sensor resolution — **measured on the Oppo CPH2737: 640×480 (0.3 MP)** with CameraX's default analysis strategy, and **1600×1200 (1.9 MP)** when the stream is bound at its largest size, which the app now does whenever the analysis stream *is* the capture source (and which the `highestResolution` policy also requests) | CameraX exposes no YUV photo stream on `ImageCapture` (see ADR-001); the analysis stream follows the app's resolution policy, whose default CameraX strategy picks a small size | Camera2 YUV capture session for the YUV path only; until then the still is capped at 1.9 MP on this device |
| 2 | ~~Final JPEG keeps EXIF orientation instead of being physically rotated~~ **Resolved** | Output pixels are now physically rotated (SPEC §89); EXIF orientation is normal | — |
| 3 | AE/AF "lock" is a non-auto-cancelling metering action, not a true lens-position lock | CameraX exposes no lens lock API (SPEC §61 approximation) | Camera2 `CONTROL_AF_MODE` handling if users need true lock |
| 4 | Lens labels (0.5×/1×/3×) are derived from reported physical focal lengths | No platform API for marketing lens names | Per-device naming table in `compat/` if labels prove confusing |
| 5 | NATURAL/PURE tuning values (tone curve, denoise/sharpen strengths) are restrained starting points, not evaluated on devices | SPEC §130 intentionally simple first pipeline | Real-device evaluation per AGENTS 63, then tune `ProcessingConfiguration` |
| 6 | Compressed DNG (lossy JPEG) is rejected and falls back to the JPEG path | DngReader supports uncompressed CFA only | Extend reader or use CameraX-decoded pixels |
| 7 | Black/white level and color matrices come from the DNG tags; ActiveArea masking is ignored | Simplifies MVP decode; masked pixels are treated as image area | Honor `ActiveArea`/`DefaultCropOrigin` if edge artifacts appear |
| 8 | GPS tagging uses `LocationManager.getLastKnownLocation` (coarse, cached) | No fused provider without Play Services dependency | Acceptable for geotagging; revisit with user feedback |
| 9 | Nothing records whether the flash fired: the JPEG/DNG carries no Flash tag or flash mode, so a flash photo is indistinguishable from an ambient one in metadata | `CaptureMetadata` has no flash field and `ExifMetadataWriter` writes only what the model carries (AGENTS 52: never invent) | Add flash mode to `CaptureMetadata` and write `TAG_FLASH`; the capture already knows the requested mode |
| 10 | A framing wider than 1x is served through the YUV path, so it is capped at the analysis stream's resolution — **measured 1600×1200 = 1.92 MP** — and it is never a RAW file | RAW is exposed only for the main camera, and below 1x the logical camera engages a wider physical one for which no RAW stream exists (the case SPEC §96 names). YUV was chosen over the platform JPEG so the wide frame still gets the app's restrained processing instead of the OEM's | A Camera2 YUV capture session (limitation #1's upgrade path) would raise the ceiling; a Camera2 physical-camera RAW/JPEG session could reach full resolution for the wide lens |
| 11 | The Style Tone pad has one contrast pivot (linear 0.18) and no toe, so a "strong contrast" style cannot darken the midtones without also clipping the deepest shadows: at pad X ≈ 0.45 everything below display 0.09 goes to black | `StyleEngine` applies a bounded `contrastK` about a fixed pivot; STYLE_PLAN §8.3's `contrastPivot` / `toeStrength` / `blackPointOffset` are not implemented, and the deepen term only acts above linear 0.30 | Implement a pivot/toe term in the tone stage (its own numeric tests + a `StyleVersion` bump), then let presets use it instead of leaning on the pivot |
| 12 | The palette undertone can warm the **lower** tones only; there is no highlight tint, so a style cannot ask for warm highlights *and* cool shadows. Warm Street measured on device: deep-shadow R/B **+5%** (warmer), highlight-band R/B **−1%** (marginally cooler) — the inverse of FILM_STYLE's split-tone wish | `shadowHueTint` is weighted by `exp(-l·2)`, i.e. it peaks in the deep shadows (STYLE_PLAN §11 defines Undertone as shadows/lower midtones/midtones); `temperature` is chroma-weighted, not luma-weighted, and barely moves bright neutrals | Add a luma-weighted highlight-tint term next to the shadow one and re-read the palette Y axis as a real split-tone axis (bump `StyleVersion`) |
| 13 | The developed JPEG's EXIF `DateTimeOriginal` is the **first capture of the camera session**, not the capture time: five captures over 15 min (20:34, 20:36, 20:38, 20:39, 20:48) all carry `2026:10:08 20:34:08`, while the file name and MediaStore `DATE_TAKEN` are correct per capture | The save path passes the capture clock to the **name** (`nameTimestamp`) but writes the **EXIF** from the DNG-parsed `fullMetadata.timestampMs` (`DngReader` tag 36867/306, with a `System.currentTimeMillis()` fallback) — deliberately, per the code comment — and on this device the DNG tag does not advance per capture; that DNG's own tag read back empty through the TIFF walker, so the fallback path needs the same look | Write the EXIF from the same capture clock as the name (one-line change at the two RAW-path `saveFinalJpeg` calls) or make `DngReader` reject a timestamp that predates the session — with a unit test on the tag→metadata path |

**Verified working on device:** shutter→gallery JPEG (EXIF: ISO/exposure/f-number/datetime/make/model
present, orientation normal, 3072×4096 portrait from landscape sensor); all three profiles via UI
(`natural-v2` / `pure-v1` / `system-passthrough` in the SPEC §109 logs, outputs measurably different:
NATURAL mean [38,34,26] vs PURE [40,37,28] at stddev ≈ [32,30,23]); RAW+JPEG paired names; RAW only
outputs DNG alone; SYSTEM dual RAW+JPEG in one capture (captureMs ≈ 1350); EV slider (1/3-step
conversion); flash cycle; grid overlay (pixel-verified); tap-to-focus (no crash); settings navigation;
capture refusal/backpressure and typed errors with recovery; SPEC §109 logs (capture ID, plan,
timings).

**Measured performance (12 MP RAW develop, NATURAL):** prior single-threaded baseline was
~20.6s develop+save on the same Oppo device. After parallelizing independent full-resolution
ranges across the available CPU cores, the latest device capture completed in **13.7s**
(`captureMs=1978`, `processSaveMs=13704`, pipeline `natural-v7`). Scene and thermal state
were not controlled, so this is an indicative improvement, not a controlled benchmark.
NATURAL-v7 still disables full-frame denoise/sharpen by default; the known tradeoff is more
preserved grain and less artificial edge enhancement. Repeat the same scene and profile for
comparable timing.

**Develop cost after the 2026-10-07 optimization pass:** the same `bias.dng` 12 MP capture developed
end-to-end through `DefaultImagePipeline` with a no-op encoder, best of 6 runs, measured 1184 ms
before and **728 ms** after (1.63x) on the dev-box JVM, with per-develop allocation falling from
**4811 MB to 528 MB** (9.1x) — allocation being the figure that predicts device GC behaviour, since
at 12 MP a develop is mostly short-lived buffers. Per-stage, demosaic went 562 to 142 ms and 90°
rotation 97 to 22 ms.

**On device (Oppo CPH2737, 2026-10-07, NATURAL / RAW / `FINAL_ONLY`, one scene, one session):**
`processSaveMs` fell from **18.5 s to 10.2 s mean (1.82x)** across 5 captures before and 4 after
(26.4 s total saved per photo; worst-before 17.6 s against worst-after 11.1 s is still 1.58x).
The sets ran sequentially rather than alternating, and the device was *warmer* during the after-set
(37.5-37.6 °C against 36.7-36.9 °C), which biases against the result rather than for it; `captureMs`
(0.7-1.4 s both sets, untouched by this change) is the control showing neither scene nor thermal
state moved much between them. Saved output is unchanged: 3072x4096 JPEG in both sets.
`DevelopBenchTest` reproduces the JVM figures on any machine.

**Where a device develop actually goes (2026-10-07):** `DefaultImagePipeline` now reports
per-stage durations in the debug log (SPEC 109 "processing duration"), which turns the
10-11 s above into a list. On the CPH2737 with the saved style (bloom 0.25, saturation
+0.05) the order is: **style 2.8-3.3 s**, sharpen 0.9-1.4 s, demosaic 0.5-1.1 s, sRGB output
0.8-1.0 s, auto-WB 0.5-0.8 s, chroma smoothing 0.2-0.7 s, DNG read 0.4-0.6 s, then ~1.5 s
across the remaining thirteen stages; JPEG encode is 0.25 s and the MediaStore write 0.1 s.
Two things that made this cheap to trust: the stage numbers sum to the measured
`pipeline=...` figure, and the *style* stage — two half-resolution chroma passes plus the
bloom's per-channel peak mask and bilinear upsample — is where the time actually is.
Individual stages still vary 2-3x between captures on an uncontrolled scene and thermal
state, so compare medians, not single captures.

**Shutter queue (2026-10-07):** the shutter used to be disabled for the whole develop, so a
"point and shoot" camera refused the next photo for ~10 s. The coordinator accepts up to
`maxConcurrentJobs` (2) jobs; a third is refused before acknowledgement with the existing
typed error (AGENTS 42). Captures may overlap — the camera serialises its own requests and a
capture is ~1 s — while develops queue behind one `Mutex`, because two 12 MP frames in flight
is a ~600 MB heap problem rather than a throughput win (AGENTS 45). The UI keeps the
viewfinder clear and the shutter live during a background develop, showing a compact
processing indicator instead of the full-screen overlay. Total time per photo is unchanged;
what changes is that the camera stays ready.

**Not exercised (needs different hardware or more sessions):** lens switching (device has one
lens), front camera, flash photo in dark scene (flash cycle verified at UI level only), YUV
fallback path (device reports RAW so NATURAL never fell back), long-run memory soak, full-resolution
crop quality review by eye (AGENTS §61 — human inspection pending).

### Device A/B measurements are not reliable for grain or noise

Measured on 2026-10-05: two captures of the *same static scene with identical settings* (Oppo CPH2737, grain 0%) differ by **+13%…+83% luma HF and +0.6e-3…+1.6e-3 chroma HF** band by band, with pixel correlation 0.79 — auto-exposure, auto white balance, sensor noise and small scene shifts between shutter presses swamp any grain-scale effect. The device figures in the two rows above were taken this way and are therefore **not evidence**; treat them as unverified observations. Grain and denoise behaviour is verified by the deterministic pipeline/stage tests instead. Any future device comparison of grain or noise needs a fixed exposure (or a single capture with syntactic analysis), not a pair of auto-exposed shots.

**And choose the mask carefully.** A "flat" mask built from *low gradient* pixels selects the quietest parts of the frame and excludes exactly where noise lives, so it saturates near the 8-bit quantisation floor and reports the same number for every frame. On 2026-10-06 that trap hid a real regression: four device captures all read a flat-area luma HF of 0.685-0.689 while their shadow (luma < 60) figures were 4.2, 5.9, 6.1, 8.3 and 8.5. Measure shadows by *brightness*, not by gradient.
